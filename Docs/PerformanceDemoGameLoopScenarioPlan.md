## 1. 목표와 완료 시점

플레이어가 이동·회피·조준·투척·근접 공격을 수행하고, 여러 적이 추적·공격하며, 포션 착지·장판 조합·지속 효과·피해·사망·웨이브 진행이 함께 발생하는 전투를 재현한다. 같은 동작을 개별 측정에도 재사용해 복합 전투에서 발견한 비용을 좁혀 조사할 수 있게 한다.

**세부 시나리오를 순서대로 실행하는 것은 복합 전투가 아니다.** S8에서는 이동·AI·물리·스킬·장판·피해가 같은 Unity 플레이 루프에서 동시에 상호작용해야 한다. 별도의 단순화한 전투 계산기로 기존 게임 로직을 대체하지 않는다.

완료 범위를 두 단계로 구분한다.

| 단계 | 포함할 게임 흐름 | 결과의 의미 |
| --- | --- | --- |
| 전투 루프 재현 | 실제 플레이어·적·장판·피해·사망·생성 경로와 실제 WaveController의 웨이브 진행 | 고정된 전투 공간에서 실제 전투를 재현. 맵 생성·방 이동 비용은 포함하지 않음 |
| 스테이지 루프 재현 | StageManager·StageEncounterCoordinator·방 전투 진입·웨이브 완료·방 클리어·다음 방 전환 | 실제 스테이지 진행까지 검증. 이를 완료하기 전에는 전체 게임 루프 검증 완료라고 표기하지 않음 |

첫 구현은 작은 복합 전투 하나를 끝까지 완성한다. 모든 세부 시나리오 구현을 기다린 뒤 복합 전투를 붙이는 방식은 피한다. 이후 같은 실행 동작을 S4·S6·S7에 연결하고 대표·최대 부하, 스테이지 진행, 장기 반복으로 확장한다.

## 2. 현재 구현과 보완 지점

현재 11개 시나리오는 S0 기준, S1 장판 1/5/10/20개 유지, S3 지형별 투척, S5 리퍼 개별 스킬이다. 각각 에디터에서 1회 측정했으며 실제 전투 전체의 성능을 입증하지 않는다.

| 현재 코드에서 확인한 점 | 확장 계획에 반영할 내용 |
| --- | --- |
| PerformanceDemoKind는 Baseline/Areas/Throw/Dash/Steal/Summon으로 구성 | 기존 enum 순서를 보존하고 새 종류를 뒤에 추가. 기존 에셋의 직렬화 값 유지 |
| Runner는 리퍼 시나리오에서만 플레이어를 만들고 PlayerController의 입력을 잠금 | 이동·공격 시나리오용 플레이어 준비 및 자동 입력 경로 추가 |
| PotionDriver는 포션 한 종류·단일 투척 중심이며 장판 수를 하나의 ActualCount로 기록 | 여러 포션 종류·여러 투척·원본/조합/잔류 장판을 구분한 관측 추가 |
| ReaperDriver는 리퍼 1개체와 단일 스킬 전환 관측 중심 | 여러 개체의 추적·공격·사망·스킬 이벤트를 관측하는 전투 드라이버 추가 |
| Arena 검증은 정확히 4개 공간을 전제로 함 | 기존 지형 유지, EnemyArena/CombatArena/StageFixture 추가 시 검증과 빌더를 함께 수정 |
| PotionAreaCombiner는 이미 조합된 쌍의 재조합을 차단 | 다중 조합은 독립적인 여러 쌍의 조합으로 구성. 조합 결과에 세 번째 포션을 붙이는 무한 연쇄를 성공 조건으로 두지 않음 |
| PotionCombinationSpread는 조합 효과가 도달하는 시간·영역을 관리 | 조합 성공 횟수와 효과 전파·대상 도달을 별도 관측 |
| SpawnManager.TrySpawn, WaveController.TryStartEncounter, StageManager.TryInitializeStage가 존재 | 전투 루프에서는 실제 생성·웨이브 경로, 스테이지 루프에서는 실제 스테이지 조정 경로 사용 |
| run.json은 환경·단계·캡처를 기록하나 입력·적 수·조합 성공 등은 구조화되지 않음 | 실행 조건과 기능별 관측·실패 사유를 구조화하고 스키마 버전 추가 |

실측에서 데모 UI 비용이 기준 시나리오에도 존재했고, 벽 근처 투척에는 최대 37.65~48.97ms 스파이크가 있었다. 확장 전 UI 비교 옵션과 이벤트 관측을 준비한다. 이 값만으로 클리핑·셰이더·풀링의 최적화 필요성을 확정하지 않는다.

## 3. 재사용할 실행 동작과 실제 코드 연결

시나리오는 기능별 동작을 선택하고 수량·배치·입력 시점·종료 조건을 정하는 설정이다. 거대한 새 시나리오 분기문에 전투 코드를 복제하지 않는다. 처음에는 플레이어 드라이버와 전투 드라이버 정도로 나누며, 범용 시나리오 프레임워크를 먼저 만들지 않는다.

### 3.1 플레이어 자동 조작

- 고정 경유점과 입력 시간표를 사용해 이동·대시·슬롯 선택·조준 시작/유지/해제·근접 모드 전환·공격을 실행한다.
- 실제 `PlayerController`의 행동 충돌 규칙과 입력 잠금, `PlayerMovementModule`의 물리 이동·피격 상태·접촉 피해를 거친다. 측정 중 Transform을 순간 이동시키거나 매 프레임 위치를 덮어써 이동을 흉내 내지 않는다.
- 현재 `InputReader`는 실제 Input System 콜백을 받고 값과 이벤트를 제공한다. 자동 입력 주입 API는 아직 없다. 구현 시 먼저 입력 공급 경계를 작게 추가하고 기존 컨트롤러가 같은 입력을 소비하게 한다. 기존 이벤트를 외부에서 임의 Invoke하거나 비공개 필드를 Reflection으로 수정하지 않는다.
- 입력 소스 교체는 해당 데모 플레이어에만 적용한다. 실제 키보드·마우스 입력이 자동 실행과 섞이지 않도록 하고, 다른 씬이 사용하는 공유 InputReader 에셋을 수정하지 않는다.
- `PlayerThrowingModule.BeginAim/UpdateAim/ReleaseThrow`와 `PlayerMeleeModule.TryAttack`은 화면 좌표를 받으므로 고정 월드 목표를 실제 카메라로 변환한다. 인벤토리 소비·쿨다운·조준 상태와 행동 취소도 그대로 관측한다.
- 직접 모듈을 호출하는 진단 시나리오는 허용하되 입력 중재를 건너뛰었다고 명시한다. S8 실제 전투 검증은 컨트롤러 입력 경로 통합 후 통과시킨다.
- 입력 실패를 무시하지 않는다. 예약/시도/수락/완료 횟수와 거부 사유를 구분한다. 벽에 막힌 플레이어를 측정 중 강제로 밀어 넣지 않고 경로 또는 조건을 수정한다.

### 3.2 다수 적과 웨이브

- 실제 적 프리팹의 AI·EnemyMovementModule·EnemyPathfinder·충돌·공격·피해·사망을 실행한다. 적을 플레이어 방향으로 직접 이동시키는 대체 추적 코드는 만들지 않는다.
- 적 프리팹 후보는 BombMonster/RangedMonster/Reaper 계열이다. 실제 사용 전 초기화·플레이어 타깃 등록·WaveEnemyHandle·데이터·연출 의존성을 검증하고, 통과한 프리팹만 roster로 고정한다.
- 개별 S6에서는 정해진 수를 실제 생성 경로로 배치한다. S8에서는 WaveController가 생성과 살아 있는 적 수·해제·완료를 관리한다. 드라이버가 별도 alive 카운터로 웨이브 완료를 강제하지 않는다.
- 이동 유지 측정에서는 공격·사망으로 적 수가 줄어드는 조건을 분리한다. 실제 교전 시나리오는 원본 피해·사망을 허용하고 활성 수의 시간별 변화를 기록한다.
- 기존 한 리퍼 전용 스킬 제한 데이터는 S5 진단에만 유지한다. S8 기본 조건은 실제 스킬 선택 규칙을 사용한다.

### 3.3 장판 조합·효과·피해

- Catalog와 PotionCombinationDatabase에서 지원되는 조합을 확인한 뒤 포션 쌍을 고른다. 같은 원소나 조합 불가 쌍을 성공 조합으로 가정하지 않는다.
- 실제 Initialize/Activate·충돌·조합 등록 경로를 통해 성공시킨다. private TryCombine을 직접 호출하거나 조합 결과 오브젝트만 만들어 성공으로 기록하지 않는다.
- 진단용 직접 생성과 실제 투척을 구분한다. 직접 생성 시나리오도 초기화 시 조합이 즉시 발생할 수 있으므로 생성 순서·등록 순서·겹침 시점을 검증한다.
- `IsCombined`만으로 전체 조합 성공을 세지 않는다. 일반/즉시/상속 효과 등의 지원 분기를 확인하고 조합 확정 지점에 중복 없는 관측을 추가한다. 원본 쌍 ID·조합 종류·결과 형상·피해 또는 전파 도달을 대조한다.
- 조합 성공, 조합 효과의 전파 시작/도달/종료, 대상 피해·상태 적용을 각각 기록한다. 이미 조합된 장판의 재조합이 허용되는 규칙 변경은 이번 작업 범위가 아니다.

### 4.1 S8 최소 전투의 예시 시간표

시간표는 자동 입력의 예시이며 실제 공격·인벤토리·AI 시간을 확인한 뒤 조정한다. 성공을 위해 피해량·쿨다운을 매 프레임 덮어쓰지 않는다.

| 구간 | 자동 입력 및 게임 동작 | 확인할 이벤트 |
| --- | --- | --- |
| 준비 | 실제 플레이어·서비스·고정 공간·초기 인벤토리 준비 | 참조/슬롯/타깃/스폰 지점 유효 |
| 워밍업 | 별도 동일 fixture로 이동·투척·교전을 예열하고 정리 | 캐시 준비, 측정용 전투를 미리 소진하지 않음 |
| 측정 시작 | 새 전투 상태에서 Measure 기록, 짧은 선행 구간 후 실제 1웨이브 시작 | Spawn 요청/성공·웨이브 시작 |
| 초반 교전 | 경유점 이동·대시·포션 A/B 순차 투척 | 이동 거리·실제 소비·착지·조합 확정 |
| 중반 교전 | 적들이 추적하며 장판 통과, 플레이어 조준/근접/회피 | 적 공격·피해·상태·사망·스킬 |
| 웨이브 전환 | 실제 살아 있는 적 해제 후 WaveController가 다음 웨이브 시작 | AliveEnemyCount·Released·완료 상태 정합성 |
| 전투 종료 | 정해진 완료 조건 충족 후 짧은 후행 구간, 캡처 닫기 | CombatCompleted 또는 실패/시간 초과 |
| 정리 | 입력 해제·실행 취소·런타임 씬 및 관련 자원 정리 | 잔류 오브젝트·이벤트 구독·서비스 참조 |

최소 전투의 첫 목표는 타임아웃 내 2웨이브 완료다. 플레이어 사망·공격 실패·포션 부족 때문에 끝나지 않으면 그 결과를 실패로 기록한다. 대표 측정에서는 플레이어 패배도 정상 게임 결과일 수 있으므로, 시나리오별 허용 종료 결과와 필수 이벤트를 명시한다.

## 6. 측정 구간과 재현성

### 6.1 구간을 나누는 기준

- S6 이동 유지: 스폰·격자 준비는 Setup, 추적은 Measure. 초기 스폰 비용을 포함하지 않았음을 기록한다.
- S4 생성/조합: 조합을 유발하는 투척·등록·겹침과 결과 생성이 Measure 안에서 발생해야 한다. 준비 단계에서 조합이 끝나면 실패한다.
- S8 전투: 측정 전에 서비스와 지형을 준비하고, 웨이브 시작·스폰·교전·사망·다음 웨이브는 Measure 안에 포함한다.
- S8_StageLoop: 방 진입/전환을 포함하는 구간과 전투 구간을 이벤트로 식별한다. 별도 맵 생성 측정을 추가할 경우 같은 통계로 섞지 않는다.
- S9 수명: 사이클별 측정과 정리 후 관측을 구분한다. 메모리 스냅샷을 뜨는 동안의 정지를 일반 CPU 통계에 포함하지 않는다.

현재 분석기는 캡처 경계 프레임을 통계에서 제외한다. 투척/스폰이 첫 프레임에 몰려 비용이 빠지지 않도록 Measure 안에 선행·후행 여유를 두고, 이벤트 프레임과 경계 제외 여부를 별도 보고한다. 선행·후행 프레임이 이벤트/유지 통계에 얼마나 포함됐는지도 명시한다. 이벤트가 빠진 캡처를 정상 비교 자료로 승인하지 않는다.

### 6.2 입력·시간·랜덤

- 이동 입력은 기존 FixedUpdate 소비 시점에 맞춘다. 액션 입력은 게임 시간/고정 틱 기준의 시간표를 사용하고 실제 수락 틱·프레임을 기록한다.
- 벽시계 시간은 타임아웃·긴 프레임 중단 감지에 사용한다. 지연된 입력을 한 프레임에 몰아서 재생해 인위적 Burst를 만들지 않는다. 지연·누락 정책과 실제 시차를 기록한다.
- 히트스톱·쿨다운·슬로우 등 원래 시간 동작은 유지한다. 동일 seed라도 물리·코루틴·프레임 순서 때문에 결과가 완전히 같다고 가정하지 않는다.
- 첫 검증은 같은 seed 3회. 이후 고정된 여러 seed 집합으로 확장하고 seed별 결과를 분리한다. 기존 반복별 seed 변화 정책과 새 정책을 명시적으로 구분한다.
- 고정 입력 시간표와 이동 경로를 저장하고 실제 이동 거리·도달점·수락 행동 수로 재현 정도를 검증한다. 단순히 정해진 시간이 지났다는 이유로 통과시키지 않는다.

### 6.3 원본 게임 조건과 진단 조건

S8 기본 전투는 실제 체력·인벤토리 소비·피해·쿨다운·사망을 유지한다. 기존 데모의 고체력 사본을 그대로 대표 전투에 사용하지 않는다. 적 수를 유지하기 위한 무적·고체력·자동 보충은 진단용 변형으로만 만들고 별도 이름과 변경값을 기록한다.

VFX OFF 비교에서도 콜라이더·타이밍·피해·스킬 상태는 유지해야 한다. 경고 오브젝트 전체를 비활성화해 게임 로직까지 멈추는 방식은 비교군으로 인정하지 않는다. 데모 UI, 실제 게임 HUD, 데미지 숫자, 카메라 흔들림, 오디오의 포함 여부를 각각 기록한다. 현재 데모에 빠진 실제 피드백은 기본 전투 조건의 의존성 검증 후 연결한다.

## 7. 관측 지표와 유효성

### 7.1 기능별 성공 증거

| 영역 | 기록할 증거 | 무효/실패 예 |
| --- | --- | --- |
| 플레이어 | 이동 거리·경유점, 입력 시도/수락/완료, 공격/투척·대시, HP·소모 | 정지 상태 지속, 잠금 미해제, 필수 행동 미수행 |
| 적 | 생성 요청/성공, 활성 수 시계열, 타깃·이동·공격·피격·사망 | 실제 AI가 꺼져 있음, 목표 상실, 개체 수 부족 |
| 조합 | 고유 쌍 ID·원소·결과·확정 프레임·전파 도달 | 시도만 있고 성공 0, 같은 쌍 중복 집계, Setup에서 선행 조합 |
| 효과 | 대상 진입/이탈·틱·피해·상태 적용/해제 | 전파 대상 없음, 외부 대상 오적용, 잔류 효과 |
| 웨이브/방 | 시작·스폰·AliveEnemyCount·완료·방 상태 | 죽은 적 미해제, 스폰 실패, 타임아웃, 진행 강제 완료 |
| 정리 | 런타임 씬·입력·이벤트·풀/서비스·활성 음원·자원 기준 복원 | 씬만 사라졌지만 전역 참조나 활성 객체 잔류 |

정확한 기대 횟수가 가능한 단일 조합은 일치 여부를 검사한다. 복합 전투는 원본 규칙에서 가능한 최소 행동·목표 범위·허용 결과를 설정하고, 계획에 없는 수량을 임의로 기대값에 맞추지 않는다.

### 7.2 성능 지표

- CPU: Main/Render Thread 평균·p50/p95/p99·최대·예산 초과 횟수, 프레임 수·측정 시간.
- 이벤트: 착지·조합 확정·효과 전파·스킬·적 스폰/사망·웨이브/방 전환의 프레임 비용·GC·호출 경로.
- 관리 할당: bytes/frame, 이벤트당 할당, 실제 GC 발생 프레임. 상위 Inclusive 비용을 중복 합산하지 않는다.
- GPU/렌더: 지원되는 목표 기기에서 GPU 시간·배치/패스·화면 점유·겹침을 별도 수집. 미수집은 0으로 표기하지 않는다.
- 수명: 같은 정리·대기 지점에서 관리 힙과 Texture/Mesh/Material·활성 오브젝트·풀 보유 수. 초기 캐시와 반복 증가를 구분한다.

새 마커 예: `PerfDemo.PlayerInput`, `PerfDemo.SpawnWave`, `PerfDemo.CombineCommit`, `PerfDemo.ComboShape`, `PerfDemo.ComboSpread`, `PerfDemo.WaveTransition`. CPU 마커는 동기 호출 범위만 감싸고 코루틴 yield를 가로질러 열어두지 않는다. 원본 처리 비용을 재려면 조합·형상 처리의 실제 호출 지점에 마커를 둔다. 외부 폴링만으로 내부 함수 비용을 측정했다고 표기하지 않는다.

관측은 이벤트 기반 카운터와 미리 준비한 버퍼를 사용한다. 매 프레임 전체 씬 검색·문자열 생성·CSV 쓰기를 피하고 측정 종료 후 저장한다. 드라이버·관측 자체의 비용도 확인한다.

### 7.3 저장과 판정

- run.json에 코드 리비전, 설정 스키마, 원본 데이터/변경값, 입력 시간표 ID, roster/wave plan, seed 정책, UI/VFX/오디오 조건, 실제 수량·성공 카운터·종료 결과를 추가한다.
- events.csv는 구조화된 이벤트 유형·대상 ID·쌍/웨이브/사이클 ID·프레임·고정 틱·게임/실제 시간·결과를 지원한다. 기존 컬럼 소비자와의 호환 또는 버전 분기를 둔다.
- 캡처 이름은 시나리오·변형·반복·사이클을 구분하고 기존 결과를 덮어쓰지 않는다. 상태 변경과 중단 시에도 캡처를 닫고 완료 여부를 기록한다.
- `실행 성공`, `기능 검증`, `캡처 검증`, `성능 목표 판정`을 분리한다. 기능이 실패한 저비용 캡처는 정상 성능 기준으로 쓰지 않는다.
- 목표 플랫폼/FPS·해상도·대표 적 수·동시 포션/리퍼 수·허용 지연은 기준 측정 전에 고정한다. 정해지기 전에는 실험값과 후보로 표기하고 제품 합격을 선언하지 않는다.
- 반복별 분포를 먼저 보고한다. 평균의 평균으로 p95를 만들지 않으며 원본 프레임을 합칠 경우 표본 수·구간·조건을 명시한다. 변경 전후는 같은 seed·입력·활성 수와 이벤트 완료량이 비교 가능한지 먼저 검사한다.

| 3. 부하 확장 | S8 대표/최대, S4 벽/분산, S5 다중 리퍼·연출 비교 | 기능 규칙을 유지한 상태에서 부하 차이가 실제로 재현됨 |
| 4. 제품 환경 기준 | 화면 있는 Development Build, 고정 조건·같은 seed 3회, UI/연출 비교 | 목표 기기에서 유효 캡처·반복 편차·병목 호출 경로 확보 |
| 5. 스테이지 진행 | StageManager/EncounterCoordinator 연결, S8_StageLoop | 방 진입·잠금/해제·전투·방/스테이지 완료를 원본 경로로 통과 |
| 6. 반복 수명 | S9의 10회 검증 후 30회 확장, 고정 정리 지점 메모리 비교 | 잔류·자원 증가 추세를 설명할 수 있고 실패/중단 후 재실행 가능 |
| 7. 최적화 선정 | 기존 가설과 실측·게임 예산 비교, 하나씩 개선 후 같은 조건 재측정 | 원인 귀속·반복 개선·게임 동작/시각 회귀 없음 |

단계 1부터 실제 게임 동작을 끝까지 실행하며, 단계 5까지 검증해야 스테이지를 포함한 게임 루프 범위를 충족한다. GPU·메모리 계측은 지원 조건과 별도 산출물 준비 여부를 표시한다. 초기 구현에 모든 조합과 60적·30사이클을 한꺼번에 실행하지 않는다.

## 9. 검증 항목과 산출물

### 기능·운영 검증

- 씬 생성 후 재열기·참조 검사, 기존 S0/S1/S3/S5 회귀.
- 입력 잠금·행동 충돌·인벤토리 부족·플레이어 사망·스폰 실패·조합 불가를 각각 명확한 결과로 기록.
- 정상 완료, 워밍업/투척/조합/교전 중 중지, 에디터 플레이 종료, 실패 후 재실행.
- 실제 피해·상태·사망·웨이브 카운트 정합성, 조합 불가 쌍이 성공으로 기록되지 않음.
- UI/VFX 비교군에서 게임 동작·수량·성공 이벤트가 동등하며 변경 조건 외 데이터가 동일함.
- 측정에 필수 이벤트가 존재하고, raw 내부 마커·기대 샘플·경계 프레임·runtime 메타데이터를 대조.
- 정리 후 런타임 씬뿐 아니라 서비스·타깃·입력·이벤트·사운드·풀 소유권까지 복원.

### 산출물

1. 확장된 PerformanceDemoScene과 설정 에셋, 실제 게임 코드를 재사용하는 자동 입력/전투 드라이버.
2. 시나리오별 조건·기능 관측이 포함된 run.json/events.csv/raw 및 이벤트 프레임 분석 결과.
3. 기존과 동일한 CLI/MCP 실행 경로와, 새 종류·변형·사이클을 구분하는 보고서.
