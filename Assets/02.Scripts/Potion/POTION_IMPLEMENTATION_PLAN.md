6. 조사 시작 시 이미 수정된 코드·씬·에셋이 다수 있었다. 이는 기존 작업이며 후속 단계에서도 덮어쓰거나 되돌리지 않는다. 매 단계 시작 시 작업 트리를 다시 확인한다.

## 2. 기획 우선순위

- 사용자 절대규칙 → Notion의 명시적 정정 → 상세 구현 표 및 계산 예시 → 상단 요약 표 순서로 해석한다.
- 사용자 확정: 장판 효과를 받는 적과 플레이어의 처리 로직은 동일하다. 대상 선정 후에는 같은 Receiver/상태 실행기/인터페이스 수치 전달 경로를 사용하며, 적 전용 장판 알고리즘을 추가하지 않는다. 이 지시는 대상 필터를 모두 Both로 바꾸라는 의미로 확대하지 않는다.
- 이전 첨부 이미지와 기존 코드 수치는 새 기획의 근거로 사용하지 않는다.
- 명시적 정정에 따라 지속형 조합의 형태만 타원으로 유지한다. 고정 복합 반경 2.25, 일괄 4초 수명, 기화의 타원 판정은 적용하지 않는다.
- 맹독화염 중독 시간처럼 명시적 정정 없이 충돌하는 항목은 아래 미결정 목록에 남긴다.
- 서리는 최신 상세 규칙에 따라 스택 금지의 예외다. 원문의 일반적인 '스택 없음' 및 과거 둔화 체크리스트보다 서리 전용 규칙을 우선한다.
- 수치는 ScriptableObject 설정으로 관리하고, 대상·남은 시간·다음 Tick·시전자 정보는 런타임 객체에서 관리한다.

### 서리 전용 규칙 (최신 변경 반영)

- 기본 서리·열충격·맹독 서리·빙전·흡혈의 서리의 장판 Tick마다 서리 +1. 기화+서리는 즉발 피해만 주며 스택을 적용하지 않는다.
- 1스택은 이동 배율 0.85, 2스택은 0.70이다. 3스택 도달 즉시 2초 빙결을 발동하고 스택을 0으로 초기화한다.
- 빙결 중에는 서리 스택을 증가시키지 않는다. 피해 Tick은 계속 실행한다. 빙결과 빙전의 짧은 마비는 별도 시간으로 관리한다.
- 장판 이탈 시 서리 스택은 0으로 초기화한다. 이미 발동한 빙결의 이탈 후 존속과 겹친 장판의 이탈 기준은 미결정 항목에 기록한다.
- 서리 섭취는 기존대로 즉시 15 피해와 2초 이동 불가이며, 스택 3회를 거칠 필요가 없다.
- 진입 즉시 첫 Tick 규칙을 적용하면 단일 서리에서 t=0에 1스택, t=1에 2스택, t=2에 빙결, t=3에는 피해만 발생한다. 내부 총 피해 20은 유지된다.
- 데이터에는 Tick당 스택 증가량, 빙결 임계 스택, 단계별 이동 배율, 빙결 시간을 표현한다. 현재 스택·출처·빙결 만료 시각은 대상 런타임이 관리한다.

### 공통 실행 규칙

- 장판 진입/재진입 즉시 1회, 이후 Interval 반복. 같은 대상의 여러 Collider는 하나의 대상으로 처리한다.
- 장판 수명은 생성 시점 기준이고 종료 시각과 같은 시각에는 추가 장판 Tick이 없다. 화염은 0/1/2/3초 총 32 피해.
- 화상·중독·마비의 강도는 더하지 않는다. 서리만 최대 3스택을 사용한다. 서로 다른 상태는 공존한다. 겹친 장판의 피해 주기 및 서리 스택 통합 방식은 아래 미결정 참조.
- 서리 이탈 시 스택을 초기화한다. 겹친 서리 장판 중 하나만 이탈했을 때의 처리는 미결정이다.
- 이동 제한은 이동에만 적용한다. 공격·투척·피격·애니메이션을 별도로 차단하지 않는다.
- 이미 적용된 잔류 DoT는 장판이 사라져도 유지한다. 사망/파괴된 대상에는 이후 피해를 전달하지 않는다.
- 지속 조합은 두 원본 장판을 먼저 조합 완료로 표시하고 원형 판정을 끈 뒤 타원 판정으로 전환한다. 세 번째 포션과 재조합하지 않는다.
- 타원은 32정점, 중심은 두 중심의 중점, 큰 원의 반경 r과 중심 거리 d에 대해 장축 반경 d/2+r, 단축 반경 sqrt(r*(d+r)). d<0.1이면 원에 가깝게 처리한다.
- 공통 투척 설정은 비행 속도 10, 최대 거리 8이다. 현재 외부 조준 코드와의 연결 제한은 아래에 기록한다.

## 5. 인터페이스에 수치만 전달하는 설계

흐름: 포션 데이터 → 순수 수치 계산 → 포션 내부 실행기(착탄/장판/잔류/섭취 시간 관리) → 포션 내부 인터페이스 전달부 → 기존 Interface 구현체.

| 계산 결과 | 기존 인터페이스 호출 | 실제 상태 변경 책임 |
|---|---|---|
| HP 피해량 d>=0 | `IDamageable.DecreaseHealth(d)` | 대상 구현체 |
| HP 회복량 h>=0 | `IDamageable.RestoreHealth(h)` | 대상/시전자 구현체 |
| 갈증 Delta<0 | `IThirstable.DecreaseThirst(-delta)` | 대상 구현체 |
| 갈증 Delta>0 | `IThirstable.RestoreThirst(delta)` | 대상 구현체 |
| Delta=0 | 호출 생략 | 없음 |

- 계산기는 Transform, 대상 객체, Coroutine, 실제 HP 저장소를 수정하지 않는다. 계산 결과에 피해/회복/갈증 변화량을 별도로 둔다.
- 전달부는 포션 내부 한 경로로 모은다. 인터페이스에는 포션 데이터, 원소 enum, 상태 객체 대신 float 수치만 전달한다. 원소·상태·시간·소유자는 포션 내부에서 관리한다.
- 흡혈은 기존 `IDamageable.CurrentHealth`를 호출 전후 읽고 `max(0, before-after)×ratio`를 계산해 소유자의 RestoreHealth로 보낸다. HP 직접 쓰기는 하지 않는다. 현 구현처럼 동기적으로 피해가 반영되는 계약을 전제로 한다.
- 실제 피해를 반환하는 새 인터페이스는 이번 범위에서 추가하지 않는다. 추후 비동기 피해/별도 방어 시스템이 생기면 외부 계약 검토가 필요하다.
- 잔류 실행기는 장판이 파괴되어도 유지되는 Receiver 쪽에서 관리하고, 원인 포션·소유자 인터페이스·흡혈률을 보존한다.
- 상태 효과는 별도 포션 런타임에서 계산한다. 이동 배율 출력은 준비할 수 있지만 외부 이동 시스템에 강제로 Rigidbody 이동을 덧씌우거나 private 필드를 Reflection으로 바꾸지 않는다.
- 외부 IThirstable에는 현재/최대 갈증 조회가 없다. 포션 측에서 최종 0~100을 재계산한다고 주장할 수 없다. 현 EntityThirst는 설정된 최대값으로 Clamp하며 Player 프리팹의 최대값은 100이다.

### 이동 연결 최소 수정안 — 3단계에서 플레이어 연결 구현

대시 정책은 사용자 지시로 확정: **둔화는 무시하고 빙결·마비만 적용한다.** 일반 이동에는 서리 스택의 감속을 적용한다.

권장 흐름: `PotionStatusEffectState → PotionEffectReceiver.MoveSpeedMultiplier → PlayerStatus.Speed/DashSpeed → PlayerMovementModule`.

1. 스택 증가, 이탈 초기화, 빙결/마비 타이머와 우선순위는 모두 Potion 안에서 처리한다.
2. Receiver는 최종 배율 하나를 노출한다. 정상 1, 서리 1스택 0.85, 2스택 0.70, 빙결/마비 0. 빙결 또는 마비가 활성인 동안 0을 우선하며 배율을 중복 곱하지 않는다.
3. Potion 밖에서는 `PlayerStatus.cs`의 이동 관련 프로퍼티만 작게 수정한다. 기본 속도 필드는 보존하고 일반 이동 Speed에만 현재 배율을 곱한다. DashSpeed는 빙결·마비일 때만 0이고 그 외에는 기본 대시 속도를 반환한다. Receiver가 없으면 정상 배율 1을 사용한다.
4. `PlayerMovementModule.cs`는 이미 CanMove, Speed, DashSpeed를 사용하므로 변경하지 않아도 된다. 이동 로직·대시 코루틴·입력 처리를 포션으로 옮기지 않는다.
5. 배율을 매번 조회하므로 상태 해제 시 원래 속도로 돌아온다. 속도를 차감했다가 더하는 복구 로직이나 이벤트 구독은 필요 없다.

설계 예시(실제 구현은 Receiver.GetMovementSpeed를 통해 동일한 배율을 조회):

```csharp
private float MovementMultiplier =>
    _potionEffectReceiver != null ? _potionEffectReceiver.MoveSpeedMultiplier : 1f;
public bool CanMove => MovementMultiplier > 0f;
public float Speed => _speed * MovementMultiplier;
public float DashSpeed => CanMove ? _dashSpeed : 0f;
```

확정된 대시 정책을 반영한 예시다. 서리 1·2스택에서는 CanMove가 true이므로 대시 속도는 그대로이고 빙결·마비에서는 false이므로 대시 시작이 막힌다. 진행 중인 대시는 변위만 0이 되고 시간·쿨다운은 기존 흐름을 유지하는 최소 수정안을 제안한다. 대시 자체 취소는 별도 변경이며 현재 권장안에는 포함하지 않는다.

대안으로 이동 배율 인터페이스를 신설할 수 있으나, 현재 PlayerStatus가 이미 Receiver를 참조하므로 이번에는 필요성이 낮다. 적 이동 구현이 생겨 공통 계약이 필요할 때 검토한다. HP·갈증은 계속 기존 Interface에 수치만 전달하며 이 논의로 그 경계를 바꾸지 않는다.

#### 이번 구현에서 사용한 기본 정책 (기획 확정과 구분)

- 강도가 다른 동일 상태는 강한 효과를 유지하고 재적용 시간만 갱신한다. DoT 강도는 초당 피해, 둔화는 감속 비율로 비교한다. 강한 효과를 유지할 때 그 효과의 시전자도 유지하고, 같은 강도는 최신 출처로 교체한다. 사용자에게 선택 질문을 제시했으며 별도 답변 전까지 문서의 권장안을 기본값으로 사용했다.
- 재적용은 남은 시간을 새 Duration으로 설정한다. 기존 주기는 보존한다. 강한 효과가 유지되더라도 새 Duration에 맞춰 만료가 갱신된다는 의미다.
- 겹친 서리 장판은 대상의 스택 하나와 다음 누적 시각을 공유하여 겹침만으로 누적이 빨라지지 않는다. 마지막 서리 장판 이탈 시 초기화한다.
- 이미 발동한 빙결은 장판 이탈로 취소하지 않고 남은 시간 유지한다. 겹침·빙결 이탈 정책은 기존 권장안을 구현 기본값으로 사용했으며 후속 기획 확정 시 변경할 수 있다.
- 주기 상태의 첫 Tick은 데이터 ApplyImmediately를 따른다. 기본 false는 한 주기 후 실행이며, 기존 마비 API는 즉시 첫 정지를 유지한다.

#### 후속 단계 연결 계약

- 새 상태 적용: `receiver.ApplyStatus(effectDefinition, source)` 또는 수치 스냅샷 `PotionStatusApplication`을 전달한다.
- 서리 장판 진입/이탈: `EnterFrostArea(sourceId)` / `ExitFrostArea(sourceId)`. 장판 Tick에서는 `AddFrostStacks(settings, source, amount, tickInterval)`를 호출한다.

- 기존 장판 피해/조합 실행 경로 및 흡혈 지급 정책은 4~7단계 범위다. 이번에는 새 상태 피해 경로가 인터페이스 전달부를 사용한다.

### 7단계 — 흡혈 4조합·기화 4조합 연결 (2026-09-29)

#### 구현한 것

- 흡혈의 화염·독·서리·전류는 Potion 내부 조합 기본 데이터에서 `InheritThrownEffectsFrom`과 흡혈률 0.20을 지정한다. 실행 시 실제 조합에 사용된 원소 포션의 `ThrownProfile`을 찾아 장판 수명·Tick·잔류·서리·마비 설정을 그대로 재사용한다.
- 직접 장판 피해와 상태 피해가 반환한 `PotionDamageResult.ActualDamage`에만 흡혈률을 곱한다. 방어·Clamp·남은 HP를 반영한 실제 감소량이므로 피해량이 대상 HP보다 커도 초과분을 회복하지 않는다.
- 화상·중독 상태의 `PotionEffectSource`에 원래 조합과 시전자를 보존한다. 조합 타원 장판이 사라진 뒤 실행되는 잔류 Tick도 같은 시전자에게 20%를 회복한다.
- 흡혈의 화염은 장판 32+잔류 8, 흡혈의 독은 장판 25+잔류 15를 기준으로 각각 총 8 회복한다. 흡혈의 서리는 장판 20에서 4, 흡혈의 전류는 장판 24에서 4.8을 회복한다.
- 화염 폭발·독성 증기·빙결 폭발·방전은 각각 Fire·Poison·Ice·Lightning 속성의 Impact 30만 가진다. 반경 2.5 원형 조회에서 Receiver를 HashSet으로 중복 제거해 대상당 한 번만 적용한다.
- 기화 조합은 타원 장판을 생성하지 않고, FloorTick·FloorExit·상태 효과도 만들지 않으며 두 원본 장판을 즉시 제거한다. 조회 중심은 기화 포션의 착탄 위치다.
- 흡혈 지속 조합은 기존 타원 형태와 두 원본 선점 방식을 유지하므로 중복 조합과 세 번째 포션 재조합이 차단된다.

#### 검증 결과와 한계

### 8단계 — 기본 에셋·통합 체크 및 외부 연결 인계 (2026-09-29)

#### 정리한 것

- Potion 내부 런타임 기준 에셋은 단일 6종과 활성 조합 14종이다. 파일명은 각각 `PotionElement`와 `PotionCombination` enum 이름에 맞춰 `Resources.Load` 경로를 보장한다. 새 기획에서 제외한 `PurifyingLife`는 내부 기본 프로필을 만들지 않고 외부 DB와 enum ID만 직렬화 호환용으로 유지한다.
- 외부 `PotionDatabase` 6종과 `PotionCombinationDatabase` 15종은 수정하지 않았다. 레거시 에셋의 enum을 키로 내부 기본 프로필을 조회하므로 기존 인벤토리·프리팹 참조를 유지하면서 새 실행 수치를 사용한다.
- `Tests~/ValidatePotionAssets.ps1`을 추가했다. 내부 20개 에셋의 존재·핵심 수치·GUID 중복, 외부 DB의 6+15 에셋 참조, `PotionGroundArea.prefab`의 AreaEffect/Combiner/Shape 및 DB 연결, `Player.prefab`의 Receiver 연결을 패키지 없이 검사한다.
- `POTION_INTEGRATION_HANDOFF.md`에 현재 런타임 연결과 외부 연결 대기 항목, 재현 명령을 분리해 기록했다. 투척 거리·비행 속도·충돌 착탄·적 수신기/이동·Unity 플레이 모드는 실제 연결 완료로 표시하지 않았다.

#### 검증 결과와 한계

- 에셋·통합 검사 통과: 내부 단일 6종+활성 조합 14종, 내부 GUID 20개 고유, 외부 DB 단일 6종+조합 15종 참조, 장판 프리팹/플레이어 Receiver 진입점 연결을 확인했다.
