# 포션·적 탐색 최적화 실행 계획

작성일: 2026-10-16  
상태: 2026-10-19 재개 작업에서 Build-v2 core 20개 시나리오 × 3회 측정·분석 완료, 유효 캡처 60개 / 무효 0개. 최종 수치와 반복별 작업량은 `Docs/OptimizationResults.md`에 기록했다. 원본·개선 구현과 일반 게임의 Original 기본값은 유지한다. 전체 suite·장기 수명 검증 및 조합 순간 끊김 추가 개선은 남아 있다.

사용자 요청에 따라 원본·개선 두 버전을 유지한다. 원본 알고리즘 파일을 보존하고 개선 구현은 이 폴더에 둔다. 실제 게임의 기본 경로는 Original로 유지하며, 데모 시나리오에서만 개선 버전을 선택한다. 본문의 최종 경로 통일 원칙보다 이 두 버전 보존 조건을 우선한다.

## 1. 목표와 범위

기존 PerformanceDemo 환경에서 병목을 재현하고, 게임 동작을 유지하면서 비용을 줄인다. 포트폴리오에는 실제 측정으로 확인한 변경과 결과만 기록한다.

| 실행 순서 | 대상 | 해결하려는 문제 | 주요 지표 |
|---|---|---|---|
| 1 | 상태이상 GC | 반복 상태 조회와 타임라인 갱신의 임시 객체 생성 | 해당 함수 및 PlayerLoop GC bytes/frame |
| 2 | 착탄·조합 부하 | 착탄과 조합 시 특정 프레임에 집중되는 생성·계산 | 구간별 ms/call, 이벤트 프레임 시간, p95/p99, 예산 초과 프레임 수 |
| 3 | 적 탐색 비용 | 적마다 반복하는 물리 조회와 대상 확인 | 탐색 ms/call, 호출 수, FixedUpdate µs/call 및 ms/frame |

실행 순서는 수정 범위와 검증 난이도를 고려한 것이다. 순간 끊김의 중요도는 착탄·조합이 높다. 상태이상 GC 개선이 예상보다 커지면 원인 확인까지만 마치고 조합 계측으로 진행한다.

## 2. 기존 환경과 작업 위치

- 검증 씬: `Assets/01.Scenes/Optimization/PerformanceDemoScene.unity`
- 기존 측정 코드: `Assets/02.Scripts/PerformanceDemo/`
- 개선 비교용 코드와 작업 기록: `Assets/02.Scripts/Optimization/`
- 기존 보고서: `Docs/PerformanceDemoGameLoopProfilingReport.md`
- 실행별 결과 보관 위치: `Logs/Optimization/<실행 식별자>/`
- 공유할 최종 요약: `Docs/OptimizationResults.md`에 작업 종료 후 작성

씬을 복제하는 대신 기존 시나리오를 활용하고 부족한 재현 조건만 추가한다. Unity의 기존 자동 실행·raw 분석 경로를 먼저 확인한 뒤 연결하며, 측정기를 중복 구현하지 않는다.

### 원본과 개선 코드를 관리하는 원칙

1. 작업 시작 시 현재 변경사항을 확인하고 기준 코드의 커밋을 기록한다. 관련 없는 작업은 보존한다.
2. 계측만 추가한 동일 코드로 개선 전 기준을 측정한다. 개선 후에도 같은 계측을 유지한다.
3. `Optimization`에는 비교 실험에 필요한 최소 구현과 실행 연결 코드를 둔다. 게임 코드 전체나 프리팹을 복사하지 않는다.
4. 비교가 필요한 경우 실행 시작 시 원본/개선 경로를 선택하도록 구성한다. 선택은 측정 구간 전에 확정한다.
5. 기존 MonoBehaviour에 의존하는 개선은 실제 원본 위치에서 수정할 수 있다. 이때 이전 커밋과 동일 시나리오를 사용해 비교하고, `Optimization`에는 변경 설명과 재현 방법을 남긴다.
6. 원본·개선 알고리즘을 각각 보존한다. 공통 게임 컴포넌트에는 선택 연결만 추가하여 두 버전의 게임 규칙이 별개로 바뀌지 않게 한다. 개선 코드의 실제 게임 기본 적용은 이번 비교 구현과 구분한다.

## 3. 공통 측정 규칙

### 기준 확보

- [ ] Unity 버전, 실행 환경, 코드 커밋, 시나리오 설정을 기록한다.
- [ ] 해상도, 품질, 그래픽 API, VSync, 목표 프레임 설정을 동일하게 유지한다.
- [ ] 시드, 적 수, 투척·조합 수, 실행 시간, UI 표시 상태를 고정한다.
- [ ] Demo UI는 끄고 워밍업 및 Setup/Cleanup 구간을 통계에서 제외한다.
- [ ] Deep Profile OFF를 기본으로 한다. 할당 스택 진단은 별도 캡처로 구분한다.
- [ ] 개선 전후 조건별로 최소 3회씩 유효 실행을 확보한다. 가능하면 전후 실행을 번갈아 진행한다.
- [ ] 실패한 실행은 이유와 원본을 보존하고 정상 결과와 섞지 않는다.

### 해석과 결과 보존

- 기존 보고서는 병목 후보 탐색 자료다. 이번 변경의 개선 전 기준은 동일한 새 환경에서 다시 확보한다.
- 전체 프레임 시간에는 에디터·표시 대기가 섞일 수 있다. 함수 비용, PlayerLoop, 표시 대기를 구분한다.
- GC.Alloc는 할당량이며, 실제 GC 수집 시간이나 메모리 누수량과 같지 않다.
- 호출당 비용과 프레임당 비용을 함께 본다. 호출 횟수나 물리 스텝 수가 줄어든 결과를 계산 자체의 개선으로 오해하지 않는다.
- raw 캡처, 분석 CSV, 설정, 기능 검증 결과를 실행 식별자로 연결한다. 최악 프레임은 해당 프레임의 호출 계층으로 원인을 확인한다.
- 60FPS를 목표로 판정할 때는 16.67ms 예산을 사용한다. 33.33ms 초과도 함께 기록하며 GPU/표시 대기를 임의로 특정 게임 함수에 귀속하지 않는다.
- 에디터에서 원인을 확인하고, 최종 채택 여부는 목표 기기의 Development Build에서도 같은 조건으로 확인한다.

## 4. 1단계: 상태이상 GC

### 확인할 코드

- `PotionStatusVisual.LateUpdate` 및 상태 활성 여부 조회
- `PotionEffectReceiver.IsInStatusArea`
- `PotionAreaEffectTracker.HasStatus`
- `IPotionEffectData.GetEffects`
- `PotionAreaTimeline<T>.Synchronize`

현재 소스에는 `GetEffects`의 `yield return`과 `Synchronize`의 `new HashSet<T>()`, `new List<T>()`가 있다. 기존 보고서의 할당을 전부 이 코드 탓으로 확정하지 않고 호출 스택으로 확인한다.

### 실행 순서

1. 기존 `S7_Area_ContactEffects_30` 및 `S7_Combine_ContactEffects_10`에서 할당 위치와 호출 횟수를 확인한다.
2. 지속 부하를 보기 위해 적 30명이 측정 시간 동안 생존하는 진단 시나리오를 별도로 추가한다. 체력 조정 여부를 명시하고 기존 사망 포함 조건과 구분한다.
3. 상태 존재 여부를 확인하는 경로에 한해 `IReadOnlyList` 인덱스 순회 등의 할당 없는 조회를 적용한다. 모든 `GetEffects` 사용처를 한 번에 바꾸지 않는다.
4. 타임라인의 집합과 키 목록을 인스턴스 버퍼로 재사용하는 변경을 따로 측정한다.
5. 버퍼 재사용 시 콜백 중 상태 변경·종료·재진입으로 순회 데이터가 손상되는지 확인한다. 기존 키 스냅샷의 역할을 유지한다.
6. 위 변경으로 부족할 때 상태 변경 시 표시 갱신 방식을 별도 실험한다. 갱신 누락을 막기 위해 진입·이탈·만료·조합·사망 경로를 점검한다.

### 기능 유지 및 채택 조건

- 피해 횟수·총 피해량·사망 수, 상태이상 표시와 종료 시점이 동일해야 한다.
- 다중 콜라이더, 여러 장판 중첩, 장판 이탈·만료, 조합 전환, 대상 비활성화에서 정상 동작해야 한다.
- 목표 경로의 반복 할당이 감소해야 한다. CPU 비용과 초기 할당·상주 버퍼 메모리의 변화도 함께 기록한다.
- 목표는 반복 할당 제거지만 전체 PlayerLoop GC 0을 미리 보장하지 않는다.

## 5. 2단계: 착탄·조합 부하

### 확인할 코드와 계측 구간

| 코드 | 분리 측정할 작업 |
|---|---|
| `PotionProjectile` | 착탄 및 장판 생성 흐름 |
| `PotionCombinedAreaShape.Create` | 형상 생성, 벽 처리, 콜라이더 설정, VFX 연결 |
| `PotionAreaClipper`, `PotionAreaFootprint`, `PotionWallQuery` | 벽 조회와 형상 클리핑 |
| `PotionAreaMaskRenderer.SetFootprint` | 픽셀 판정, 배열·Texture2D 생성, 업로드 |
| `PotionAreaSurfaceRenderer` 및 개별 VFX 렌더러 | 머티리얼·메시·시각 객체 생성 |

계측 마커는 실행 횟수와 원인을 구별할 수 있도록 구간별로 추가한다. 예: `Optimization.Mask.Rasterize`, `Optimization.Mask.Upload`, `Optimization.Combine.Collider`.

### 실행 순서

1. 비중첩, 한 쌍, 동시 10쌍, 순차 10쌍, 단순 벽, 복잡한 모서리 조건을 기준 측정한다.
2. 긴 프레임에서 가장 큰 하위 구간을 확인하고 비용이 큰 순서로 개선 대상을 정한다.
3. 같은 형상에 대한 마스크·메시 재생성이 실제로 발생하는지 호출 횟수로 확인한다. 중복이 있으면 먼저 제거한다.
4. 배열·텍스처·메시·시각 객체의 재사용을 각각 실험한다. 풀 반환 시 참조와 상태 초기화, 자원 해제 책임을 명확히 한다.
5. 마스크 생성이 주요 비용일 때만 해상도 256/128/64 등을 비교한다. 크기별 계단 현상과 표시·판정 차이를 확인한다.
6. 워밍업은 첫 사용 비용과 반복 비용을 분리해 평가한다. 이미 존재하는 불꽃 셰이더 워밍업과 중복 작업하지 않는다.

### 주의 사항과 채택 조건

- 실제 조합 횟수, 피해 결과, 벽 잘림, 콜라이더 범위, 지속 시간이 같아야 한다.
- 해상도 감소는 화질 절충이므로 기존 표현 유지 실험과 구분하고 비교 이미지를 남긴다.
- 여러 프레임으로 분산하는 방식은 비용 제거와 구분한다. 반응 지연 및 총 처리량 변화도 측정한다.
- 단일 호출 최대, 이벤트 프레임 시간, p95/p99와 예산 초과 프레임 수를 함께 비교한다. 최대값 하나로 성공을 판정하지 않는다.
- 머티리얼 공유가 배칭을 보장하지 않는다. 셰이더·배칭 변경은 GPU/렌더링 계측에서 필요성이 확인될 때 별도 범위로 진행한다.

## 6. 3단계: 적 탐색 비용

### 확인할 코드

- `RangedEnemyController.FixedUpdate`
- `RangedEnemyController.FindPlayerInRange`
- 플레이어 몸체 콜라이더·레이어 구성과 공격/시야 판정

현재 재사용 `List<Collider2D>`가 있으므로 native 마커 이름의 `All`만 보고 배열 할당 문제로 판단하지 않는다.

### 실행 순서

1. 이동/정지 적 10·30·60명과 밀집 조건에서 탐색 시간, 조회 횟수, 반환 콜라이더 수, FixedUpdate 호출 수를 기록한다.
2. 플레이어 몸체의 실제 레이어 구성을 확인한 뒤 대상 레이어 필터를 적용한다. 필요한 콜라이더가 누락되지 않는지 검증한다.
3. 필터만 적용한 결과를 측정한 다음 대상 참조 캐시를 별도 실험한다. 감지 거리·대상 생존·활성 여부는 계속 확인한다.
4. 대상 재획득 조건과 풀 재사용 시 캐시 초기화를 검증한다. 대상이 여러 명일 수 있다면 기존 선택 규칙도 확인한다.
5. 탐색 간격 조절은 마지막에 별도 실험한다. 감지 지연 허용치를 먼저 정하고, 공격/이동 물리 갱신까지 같은 간격으로 낮추지 않는다.
6. 탐색을 분산한다면 같은 프레임에 요청이 몰리지 않는지와 최악 감지 지연을 함께 측정한다.

### 기능 유지 및 채택 조건

- 감지 경계 진입·이탈, 대상 비활성화·재등장, 적 풀 반환·재생성, 빙결/마비 해제 후 동작을 확인한다.
- 추적·공격 전환과 벽 뒤 시야 판정이 유지되어야 한다.
- 조회 자체의 호출당 비용 감소와 탐색 횟수 감소 효과를 구분한다.
- 탐색 간격 변경으로 반응성이 달라지면 동일 동작 개선으로 표현하지 않고 절충 사항으로 기록한다.

| 착탄·조합 | S4 동시 10쌍, 마스크 공유 | 최대 단일 호출 ms | 최종 문서에 3회 값 보존 | 최종 문서에 3회 값 보존 | 중앙값 24.325 → 13.742, 이벤트 프레임 185.158 → 127.430ms | 매회 조합 10회, 런타임 통과 | 비교용 유지, 프레임 예산 미달성 |
| 적 탐색 | S6 정지 적 60명, 레이어 필터 | µs/call | 최종 문서에 3회 값 보존 | 최종 문서에 3회 값 보존 | 중앙값 15.094 → 4.569, 69.7% 감소 | 매회 적 60명·사망 0명, 런타임 통과 | 단일 플레이어 데모 범위 |

대표값은 동일 지표의 실행별 값과 함께 제시한다. 마커 inclusive 시간은 하위 시간을 포함하므로 부모·자식 비용을 더하지 않는다. 감소율은 `(개선 전 - 개선 후) / 개선 전 × 100`으로 계산하며, 기준값이 0인 경우 계산하지 않는다.

## 8. 최종 완료 기준과 포트폴리오 작성

- [ ] 세 항목의 원인을 측정 근거로 설명할 수 있다.
- [ ] 각 변경은 별도로 비교했고, 최종 결합 상태에서도 기능과 성능을 재확인했다.
- [ ] 목표 기기의 Development Build에서 반복 검증했다. 실행하지 못했다면 환경 한계를 명시한다.
- [ ] 효과·피해·조합 수·감지 동작을 유지하거나 달라진 조건을 명시했다.
- [ ] 개선하지 못한 항목도 결과를 보존하고, 성과로 표현하지 않는다.
- [ ] 최종 게임 경로에 반영한 코드와 비교 실험용 코드를 구분한다.
- [ ] 포트폴리오의 모든 수치가 캡처·설정·커밋으로 추적 가능하다.

작성 예시의 숫자는 실제 결과가 확보된 뒤 채운다.

> 상태 조회의 반복 할당을 확인하고 조회 방식과 임시 버퍼 관리를 개선하여, 동일 장판 접촉 조건에서 해당 구간의 GC 할당량을 A → B bytes/frame으로 줄였다.

> 착탄·조합 처리의 세부 비용을 계측한 뒤 [실제 변경]을 적용하여, 동일 조합 조건에서 [지표]를 A → B로 줄였다.

> 원거리 적의 [실제 변경]을 적용하여, 적 60명 조건에서 [호출당 비용 또는 프레임당 비용]을 A → B로 줄였다. 탐색 간격을 변경했다면 감지 지연도 함께 명시한다.

AI 생성 코드가 포함된 경우 직접 수행한 분석·설계·변경·검증 범위를 구분한다. 실행 전 계획, 구현 완료, 측정으로 확인한 성과를 혼용하지 않는다.
